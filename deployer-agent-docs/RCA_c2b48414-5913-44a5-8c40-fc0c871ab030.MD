# RCA — Failed redeploy (run c2b48414-5913-44a5-8c40-fc0c871ab030)

## Summary
The redeploy failed at the **deploy_k8s** step. The new pod never became ready because the backend
container was repeatedly **OOMKilled (exit 137)** during startup and entered **CrashLoopBackOff**.
The deploy never reached health_check/promote, so the new code is NOT live. The previously healthy
run (21fb8b46-27e8-408c-a5ad-12da87023b9b) is still the active/serving version.

## Evidence
- Pipeline error: `CrashLoopBackOff (early): restarts=3 lastExit=137/OOMKilled` on pod
  `r-c2b48414-...-5ljgs`.
- get_pod_events: Liveness/Readiness/Startup probes all `HTTP 503`; `BackOff restarting failed
  container`; container restarted 4x then killed.
- get_tier: tier_0 "Starter" → memory request 200Mi, **memory_limit 512Mi** (hard cap). exit 137 ==
  OOMKilled at this limit.
- fetch_app_logs (failed run) shows the repeating crash loop, one cycle per ~60s at 01:12 / 01:13 /
  01:14:
  1. `Waiting for application startup.`
  2. `instant_bundle: scheduler started`
  3. `instant_bundle: warm-started from MongoDB (channels=8909 categories=126 ...)`,
     `cached payload built (gz=184 KB, raw=3591 KB)`
  4. `Application startup complete.`
  5. Immediately a burst of **hundreds of concurrent httpx calls** to api.deezer.com /
     itunes.apple.com / EPG (`instant_bundle: refreshing EPG…`)
  6. During that burst the container is OOMKilled → restart → repeat.
- nginx side-effect: `/health` proxied to 127.0.0.1:8001 returns `connection refused` then
  `upstream timed out` while the backend is memory-thrashing / restarting (and one
  `GET /health 404` — the backend route also appears not to answer /health cleanly, but this is
  secondary; the killer is the OOM).

## Root cause
The app's eager startup work exceeds the tier_0 512Mi memory limit. The instant_bundle warm-start
(8909-channel dataset from MongoDB) plus the burst of hundreds of concurrent deezer/itunes/EPG
enrichment HTTP requests kicked off immediately at boot spikes RSS past 512Mi, so the kernel kills
the container (exit 137) before it can stay ready. A prior tier_0 run succeeded ~11h earlier, so the
app was already running close to the ceiling; this run tipped over.

## Why it is not auto-fixable here
- Memory limit is dictated by the tier; a manifest edit cannot raise it above the tier ceiling
  (the platform clamps requests back to the tier limit). So this is NOT a manifest fix.
- I cannot change the tier (user action) and I cannot edit source (E1/Code). Re-running the pipeline
  unchanged would OOM again, so resume_pipeline was intentionally NOT called.

## Recommended fixes (either unblocks the deploy; ideally both)
1. **Tier upgrade (User)** — raise the deployment above tier_0 in Deployment Panel → Resources
   (tier_1 "Launch" or higher) so the startup memory spike fits, then redeploy.
2. **Code fix (E1)** — reduce peak startup memory so the app fits/launches faster:
   - Defer the instant_bundle warm-start and, critically, the enrichment burst to a background task
     AFTER the server reports ready (don't block/boot with it).
   - Bound concurrency on the deezer/itunes/EPG httpx calls (e.g. a small semaphore) instead of
     firing hundreds at once, and stream/release responses rather than holding them all in memory.
   - Ensure a lightweight `GET /health` route returns 200 quickly and independently of the bundle
     work (the probe currently sees 404/503/refused while the heavy work runs).
