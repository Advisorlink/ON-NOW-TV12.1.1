# RCA — /api/vod/test-direct returns {"streams": []} in production

## Symptom
Production (https://onnowhub.com, deployment rebrand-app-5) GET `/api/vod/test-direct?type=movie&id=tt1517268` with a valid Bearer token for TRAV26 (account id `va_956c765af1be4735`) returns `{"streams": []}` in ~0.2 s. In preview the same call returns 1–3 "GORILLA DIRECT" streams after a ~16 s catalogue fetch.

## Root cause (PROVEN)
`vod_test_provider._allowed()` calls `vesper_accounts.find_one({"id": <id from bearer>})` and compares `.username` against `VOD_TEST_ACCOUNTS`. In the **production** database the `vesper_accounts` collection is **completely empty**, so the lookup returns `None`, `_allowed()` fails, and the provider returns `[]` immediately — which matches the fast ~0.2 s response (no upstream catalogue fetch happens). It is NOT the config/`_cfg()` early-return path; all VOD_TEST_* secrets are present and correct.

## Evidence
1. list_secrets (active run 872625b7-7df7-494a-8772-bc671d3aed7d), metadata_available=true:
   - VOD_TEST_ACCOUNTS: is_empty=false, matches_expected=true (== "TRAV26")
   - VOD_TEST_BASE: is_empty=false, matches_expected=true (== "https://gorillaposition.xyz:443")
   - VOD_TEST_USERNAME: is_empty=false
   - VOD_TEST_PASSWORD: is_empty=false
   - VOD_TEST_LABEL: is_empty=false
   → `_cfg()` has every value it needs; it does not early-return.
2. mongo_query on prod DB `rebrand-app-5-test_database`:
   - `vesper_accounts.find({"id":"va_956c765af1be4735"})` → 0 documents
   - `vesper_accounts.find({"username": /^TRAV26$/i})` → 0 documents
   - `vesper_accounts.count({})` → 0 (collection exists but holds no documents)
   → the production `vesper_accounts` document for TRAV26 does NOT exist; the collection is empty.

## Why preview works but prod doesn't
Preview's database contains the TRAV26 `vesper_accounts` document; production's does not. Redeploys do NOT migrate preview data to production (only the initial deploy migrates data), so this collection was never populated in prod. `/api/vod/match` still works with the same token because JWT auth is self-contained (signed with JWT_SECRET, id embedded) and does not depend on this collection; only `_allowed()` in vod_test_provider performs the extra `vesper_accounts` username lookup that is failing.

If desired, the code can be re-confirmed, but it does not change the diagnosis.

## Fix
The production `vesper_accounts` collection must be populated with the TRAV26 account document (id `va_956c765af1be4735`, username `TRAV26`). Options:
- Copy the `vesper_accounts` data from preview → production via the DB Manager, OR
- Re-run the app's normal account-creation/sync flow against production so the account is written, OR
- Insert the document manually.
No code change and no secret change is needed — all VOD_TEST_* secrets are correct.
