# RCA — rebrand-app-5 redeploy failed at deploy_k8s (OOMKilled at 512Mi)

## Run
- Failed run: `03e4449d-ee99-4165-9817-07e5af0a3d37` (type: redeploy)
- Last healthy/active run still serving: `21fb8b46-27e8-408c-a5ad-12da87023b9b`
- Live URL (old version still up): https://rebrand-app-5.emergent.host
- Tier: tier_0 "Starter" — memory request 200Mi, **memory_limit 512Mi**, cpu 50m/250m, replicas 2.

## Symptom
`deploy_k8s` never became ready. Container terminated with **exit 137 / OOMKilled**, CrashLoopBackOff (early), restarts=3. Pod events: repeated `Startup/Liveness/Readiness probe failed: HTTP 503` and `connection refused` — these are secondary, caused by the container being OOM-killed and restarting.

## Root cause
The backend boots successfully on every attempt — logs show `Uvicorn running`, `Application startup complete`, `GET /health → 200`, and `instant_bundle: warm-started from MongoDB (channels=8909 categories=126)`. It is then **OOM-killed at the tier_0 512Mi cgroup limit** within ~60–90s of start (pods started 01:40:39, BackOff by 01:42:17), i.e. during the instant_bundle warm-start / payload rebuild — **before** the delayed 180s music warmer and 240s catchup verifier would run. So the memory spike is the warm-start rebuild over the full 8909-channel set, not the deferred background tasks.

The memory fixes shipped in this build (streaming gzip `_gz_json`, json.loads from bytes, gc+malloc_trim) lowered the **preview** worker peak to 445MB (steady ~423MB). Production warm-start from the full Mongo channel set, plus allocator fragmentation across the rebuild, pushes RSS past the 512Mi hard limit — the OOMKill proves peak reached ≥512Mi.

## Why this is not auto-fixable here
- OOMKilled (exit 137 + reason OOMKilled) at the tier memory ceiling is a resource limit, not a manifest bug. Raising memory request/limit in a manifest is silently clamped back to tier_0's 512Mi, so a manifest edit cannot help.
- The source is already optimized; no source change I can verify would bring prod peak under 512Mi.
- Re-firing the same image at the same tier would OOM identically — pipeline was not resumed.

## Resolution
Raise the deployment tier (Deployment Panel → Resources) from tier_0 (Starter, 512Mi) to at least tier_1 (Launch) or higher, then redeploy. tier_0 512Mi is below this app's production startup peak (≥512Mi; preview peak 445MB is the floor, prod warm-start exceeds the 512Mi limit).

Optional source mitigation (E1, if the user prefers not to upgrade): reduce peak RSS further during warm-start — e.g. build the instant_bundle payload in smaller chunks / avoid holding the full raw structure alongside the gzip buffer, or lower worker warm-start concurrency — to keep steady+peak comfortably under 512Mi.
